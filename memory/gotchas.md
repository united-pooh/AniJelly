# 已明确的边界

- 手册读者是开发者，侧重模块和实现，不按终端用户操作指南组织。
- 目录名称 AniJelly 不足以证明存在动漫定制功能；结论必须来自当前源码。
- Web 客户端由独立项目提供，不能凭后端接口推断具体 UI 入口或交互效果。

- 不要仅凭 PATH 未命中就判断 SDK 不存在；本机 .NET 位于 $HOME/.dotnet/dotnet。
- 弃用 Startup GET 曾承担唯一首用户初始化副作用，删 API 时要先迁移到保留 POST 并验证空库流程。
- 旧路由删除后的 404 不能证明业务功能正常；用 MVC 注册表检查删除，并让替代入口测试断言有效响应。
- 首次设置测试要自包含；依赖其他测试设置静态 Token 会导致单独执行时请求头 FormatException。

- 用户不接受原版 Web 设置、首页和配置页的默认视觉。功能/健康检查通过不能替代视觉验收；本次已批准 Apple TV 深色风格，需要统一三类页面并检查实际桌面与手机截图。

- 用户反馈第一版 Cinema 太素，希望增加色彩、毛玻璃和扁平感。不要只提高模糊半径；需要有色背景、适当透明度和清晰文字层次，同时保留首屏操作空间。

- 用户再次强调 Liquid Glass：深色磨砂卡片加背景渐变仍不足；应呈现透光、反射边缘和明确的材质层次，网页近似与 Apple 原生效果需如实区分。

- 顺序缓存server-build后不要再改构建上下文内文件（包括docker/主题说明.md）；否则最终构建会重新并行publish和webpack，可能再次OOM。文档先写完再准备缓存，或在失败后复用已完成server层单独重试Web，期间不再改上下文。

- 删除电视功能时不能凭 startTimeText/endTimeText 类名删除播放器节点；osdPositionText/osdDurationText 仍是普通视频构造与进度显示的必需节点。需真实 HTML + constructor 回归，并用实际短片验证播放，类型检查与API开流成功都不足以替代。

- 用户指出夜航登录页元素过多、整体不协调，要求先调查绝区零。不能把 CRT、磁带、票根和装饰文案逐项堆叠；应先确定唯一视觉中心、统一空间/材质/光线，再决定装饰。白色票根会与 CRT 抢主角，宣传式标题和双语铭牌增加独立注意力块。“无溢出/无遮挡”只证明布局可用，不代表审美协调。先完成调查评审，随后用户明确授权重做并更新容器；现已完成统一CRT改版。

- 接真实媒体后不能沿用保守 H.264-only 能力声明导致兼容 HEVC/HDR 也强制转码；先探测真实文件/MSE解码能力，保留兼容回退。HLS不等于视频转码，播放类型须依据真实服务端会话。HDR码流保持与显示器HDR成像分开验收。
- 后台浏览器标签的视口可能与当前可见标签不同；截图尺寸和渲染内容必须一起检查，innerWidth正确不代表截图正确。无效截图应作废，不扩大为视觉通过。

- 2026-10-13：用户明确播放信息卡顿发生在8096/web原版Jellyfin，不要只修18777夜航。原版统计必须打开即渲染已有数据，不能依赖timeupdate或等待Sessions；暂停状态和慢请求均需回归。
